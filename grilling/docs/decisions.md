# grilling — design decision record

English | [日本語](decisions.ja.md)

The decisions behind the plugin's shape, from the first release (0.1.0, 2026-09-03) through the completion of the plan (0.2.0, 2026-09-04). Each entry records the context, the decision, and its consequences. The plan and its completion record are [`docs/plugin-plan.md`](../../docs/plugin-plan.md) (Japanese); the requirements, design, and question records of the AI-DLC workflow that produced 0.2.0 are under `aidlc/spaces/default/intents/260904-plugin-plan/` in this repository.

## 1. Contributions only — no stages, agents, scopes, sensors, tools, or knowledge

- **Context** — The interaction-mode choice is defined in `core/aidlc-common/protocols/stage-protocol.md` §3 Step 2, and a plugin cannot target a protocol: contribution targets are core stage slugs. When a stage builds that question, the orchestrator reads both the protocol and the stage body, so a fragment spliced into the stage next to its question step is read at the right moment. The framework also lets a plugin ship stages, agents, scopes, sensors, tools, and knowledge files.
- **Decision** — The plugin ships `contributions/` and nothing else (manifest `contributes.overlays`): one contribution per core stage that owns a `<slug>-questions.md` — 28 of them — each splicing the same fragment, which defines the fourth option and the Step 3d procedure. Core is never modified, and the `/grilling` skill is not a dependency: the emitter does not project `skills/`, and other people's installs do not have it. Everything the mode needs is written in the fragment itself, including, since 0.2.0, the round rules, the decision tiers, and the Depth table — rather than in a `knowledge/` file the manifest would have to declare.
- **Consequences** — Disable the plugin and the vanilla three-mode workflow remains. There is nothing to refresh on upgrade except the merge itself, so the installer's upgrade refresh and its tombstone list are no-ops. The fragment is long (139 lines in 0.2.0, capped at 150 by a test) and the same prose lands in all 28 stages. The stage protocol still lists three modes, so the fragment states that Grill me is offered *in addition* to them. Claude Code's `AskUserQuestion` takes four options, so Grill me fills the last slot; a fifth mode could not be added the same way.

## 2. The plugin is named `grilling`, not `grill-me`

- **Context** — The plan named the plugin `grill-me` and placed it under `plugins/grill-me/` inside a framework checkout. It was built instead in its own repository, from the `grilling` skill it inlines. The framework's rules: a manifest name is lower kebab-case without an `aidlc-` prefix, and the host-side package ID becomes `aidlc-<name>`.
- **Decision** — The name is `grilling`, and the plugin lives at the repository root as `grilling/`, next to the `aidlc-workflows` submodule, the way deep-spec-analysis is laid out. The host package is `aidlc-grilling` in the `aidlc-plugins` marketplace; the fragment heading reads "Grill me (grilling)"; the provenance file is `grilling-install.json`; the option label stays `Grill me`. The plan was updated to the implementation rather than the implementation renamed to the plan.
- **Consequences** — The selection command is `/aidlc plugin select aidlc,grilling`, and the compose sentinel is `<!-- plugin:grilling:… -->`. The installer's `--from` takes the repository root and finds `grilling/.aidlc-plugin/plugin.json` beneath it, so a local checkout and a GitHub source archive have the same shape.

## 3. Anchors: `after-step:N` / `before-step:N` per stage; `after-questions` is not used

- **Context** — Compose implements `after-step:<n>`, `before-step:<n>`, and `end-of-steps`. The `after-questions` anchor is listed in the framework documentation, but `locateAnchor` in the compose hook has no case for it: the fragment is drop-logged as "unknown anchor" and never lands. The offline validator does not check that an anchor resolves to a step in its target stage, so a wrong anchor passes validation and fails only at compose time.
- **Decision** — Every contribution anchors right after the step that generates the stage's questions or right before the step that collects the answers, per the `TARGETS` table in `scripts/sync-contributions.ts`; all carry `order: 100`. code-generation, whose questions file is created in Step 3 (Plan Approval), uses `after-step:3` — the plan's placeholder `end-of-steps` was replaced once the stage body was read. The tests assert that every anchor resolves to a real `### Step N` heading in the core stage source and that composing into Claude and Kiro installs places exactly one block at each anchor with zero drops and a byte-identical second compose.
- **Consequences** — The orchestrator reads the fourth option next to the protocol's three. An engine version that renumbers a stage's steps would move or drop a fragment; the anchor-resolution and compose tests catch that when the submodule is bumped.

## 4. The fragment template lives in `tests/fragment-template.md`; the 28 contributions are generated

- **Context** — Twenty-eight near-identical files drift. `tests/` is never projected or composed into an install, so a file there can be the source of truth without being distributed. The framework's scaffolder (`aidlc-plugin-create.ts`) creates a dummy stage, which a contributions-only plugin does not want.
- **Decision** — `tests/fragment-template.md` is the only hand-edited prose. `scripts/sync-contributions.ts` renders the 28 files from it and its anchor table (frontmatter `target` / `plugin` / `anchor` / `order`, the `## fragment:` heading, then the template); `--check` exits non-zero on drift, naming the files, and runs in CI and in the test suite. `plugin.test.ts` compares every contribution with the template rendered for its target and checks the template's fixed tokens.
- **Consequences** — Editing a contribution directly is reverted by the next sync and fails the drift test. The template itself is not distributed; only its rendered copies are.

## 5. The live check is Claude Code only; the shipped gate covers Claude and Codex

- **Context** — The plan's verification steps asked for `aidlc-plugin-test.ts --install` on all seven harnesses and a live check on Claude Code plus one numbered-prose harness (Kiro CLI or Codex); the intent's second success metric said the same. At requirements analysis the owner chose Claude Code only for both, "for now, the rest later" (questions Q1 and Q2 of the 0.2.0 workflow). On 2026-09-05 the owner asked for a sandbox check on Claude *and* Codex, which took the shipped gate to its second harness.
- **Decision** — Automated compose verification covers the seven harness builds, compose into Claude and Kiro installs, and the shipped `aidlc-plugin-test.ts --install` gate on **Claude and Codex**. The live check runs on Claude Code only: `bun run test:live` through the Claude Agent SDK, plus the 2026-09-03 headless run, which rendered numbered prose because print mode has no `AskUserQuestion` and so doubled as a check of that rendering path. The remaining five harnesses' `--install` gate and a real numbered-prose live run are recorded as future work in the plan's completion record; the intent's second metric is overridden by the requirements.
- **Codex sandbox check (2026-09-05)** — Both sandboxes were rebuilt from `aidlc-workflows` v2.7.0-1-ga277af21 `dist/<harness>` and installed with `install.ts --project ../grilling-sandbox-<harness> --from . --harness <harness>`. Each reported `Changed 1` then `Changed 0`, 28 of 28 target stages carried the sentinel, the gate reported `CLEAN` with `Drops: 0` and `Idempotent second compose: true`, and `doctor` passed 50/0 on Claude and 44/0 on Codex. The fragment lands byte-identically on both: in `requirements-analysis.md` it occupies the same lines between `### Step 6` and `### Step 7`, under the same content hash. Codex is a store harness like Claude, so nothing is copied into the project on either.
- **Consequences** — The fragment's numbered-prose rules (the ❓ / ➡️ / `---` format, Other on line 5) are verified only through the print-mode record, not on a numbered-prose host itself. A Codex install also records one advisory drop on every compose — `runner regeneration skipped: .codex/skills not present in this install` — because `.codex/` has no `skills/` directory. It is not a dropped contribution: the gate reports `Drops: 0` and all 28 sentinels land, and a contributions-only plugin ships no stage that would need a runner. But `doctor` surfaces it as "a hook swallowed a failure and fail-opened", so every Codex install carries one advisory that has to be explained rather than fixed.

## 6. Parity with deep-spec-analysis is the ceiling, not the floor

- **Context** — The sister plugin deep-spec-analysis sets the bar for a finished plugin repository: a root README in two languages, LICENSE, an installer, a release script, a CI tag check, a decision record, `mise.toml`, and `renovate.json`. It also has stages, sensors, tools, a doctor, and a layered `src/`, which grilling has no use for.
- **Decision** — Mirror what the reference has an equivalent for, and nothing more. `install.ts` and `release.ts` are copies of the reference scripts with three constants (plugin name, repository, provenance file) and the completion notes replaced; their tests mirror the reference tests. The README structure follows the reference's seven headings. No CHANGELOG, npm package, GitHub Release asset, or CI badge, because the reference has none; no doctor and no coverage scan, because there is nothing for them to report.
- **Consequences** — Two repositories carry the same installer, so fixes are ported by hand; extracting a shared library is deferred. The reference's deep-spec-specific completion notes become two lines: the `Grill me` option appears at the next question stage, and `/aidlc plugin sync` must be re-run after an engine update.

## 7. The upstream skill's current version (rounds) is adopted, and Depth maps to decision size rather than to a question count

- **Context** — 0.1.0 mirrored an older version of the `grilling` skill: one question at a time. The current version (mattpocock/skills `main` as of 2026-09-04, `skills/productivity/grilling/SKILL.md` and `docs/productivity/grilling.md`) models the conversation as a design tree and asks the frontier — every decision whose prerequisites are settled — in one round, with dependent questions waiting for the next; renders questions as `❓ **Qn** - **title**: body` with a `➡️` recommended answer; has facts looked up by a sub-agent without blocking the rest of the frontier; ends only when the frontier is empty and understanding is shared; and deliberately sets no cap on the number of questions, offering a one-question-at-a-time opt-out through a line in `CLAUDE.md`. AI-DLC has a Depth axis (Minimal / Standard / Comprehensive) that its stages read as a rough question count.
- **Decision** — All five elements are adopted and mapped onto AI-DLC's questions file, the §3 decision / answer log pair, and the consolidated summary. Depth maps to decision size instead of count: decisions are sized XL / L / M / S / SS by two questions — reach (what else changes if this flips) and undo (how hard it is to reverse) — each tier with one judgment question, an example, and a counter-example; Minimal asks XL and L, Standard adds M, Comprehensive adds S; SS is always the agent's; when two tiers fit, the larger wins. A decision below the threshold is decided with the recommended answer and written under `### Decided assumptions (round n)` as `- [tier] decision — reason`, right after that round's questions; the consolidated summary lists every assumption for confirmation in bulk, and an objection promotes one to a question in the next round. Claude Code screens hold at most four questions, so a round of five or more is split into screens of four (the questions are independent, so a split changes nothing); the recommended option is moved first and marked `(Recommended)` for the screen only. Numbered-prose harnesses get the whole round in one message in the upstream format with the option order unchanged. A question waiting on a lookup is appended with `**Pending:**`; one the lookup settles gets `[Answer]: Resolved by lookup (round n)`. The opt-out reads `## Corrections` in the space's `project.md` by meaning, in any language, and also a request made during the interview. The option description became `Interview me in rounds of independent questions, each with a recommended answer; drill into every branch until we share the same understanding`.
- **Consequences** — The upstream's "no cap" survives as: no cap on the count, the size of the decisions limits the interview. Round and decided-assumption headings are rendered in the conversation language; only `**Mode:** grill`, `(Recommended)`, `**Pending:**`, the tier tags, and `X. Other (please specify)` are fixed tokens. The live test asserts that the first screen after choosing Grill me carries two to four questions with `(Recommended)` first; whether the questions on one screen were really independent is judged by a person reading the record. The frontier is a judgment, not a computation: two dependent questions can land in one round, and the remedy is to re-ask the affected branch in the next round.

## Selection-key environment check (NG1)

A concern raised while reverse-engineering the framework: an install whose `tools/data/harness.json` carries a `plugins` selection key (written by `aidlc-utility.ts select-plugins <names>`) enables plugins by name. Can a plugin that owns no stage and no scope be named there, and do its contributions still merge? The check is `tests/select-plugins.test.ts`, opt-in with `GRILLING_SELECT_KEY_CHECK=1` — recorded, not gating. It builds the Claude projection, copies the checkout's `dist/claude` install twice, writes the key, and runs the projection's real `hooks/compose.ts` against each copy.

Measured 2026-09-04 against aidlc-workflows `v2.7.0-1-ga277af21`:

| Install | `plugins` key | compose exit | Stages carrying the fragment | Drops | Key after compose |
|---|---|---|---|---|---|
| selected | `["aidlc", "grilling"]` | 0 | 28 / 28 | 0 | `["aidlc", "grilling"]`, kept |
| excluded | `["aidlc"]` | 0 | 0 / 28 | 1 `.drops` file with one `[advisory]` line: plugin "grilling" composed but is not enabled by `tools/data/harness.json`; run `bun .claude/tools/aidlc-utility.ts select-plugins aidlc,grilling` | `["aidlc"]`, kept |

A contributions-only plugin is therefore selectable by name, its contributions merge, and an install that excludes it says why and how to add it. The result is positive, so nothing was added to the README's Limits. The `/aidlc --doctor` row "Composed plugin surface" is not exercised by the opt-in test and remains a manual check. The run took under a second once the projection was built (`5 pass, 1 skip`; the skip is the placeholder test that keeps the file from being an empty suite when the gate is off).
