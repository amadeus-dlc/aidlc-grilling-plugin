# Functional Design — 質問

構成決定（`../../inception/domain-design/components.md`）で決めた 6 つの構成要素のうち、挙動を設計する必要があるのは Grill me の断片テンプレート（決定の木・ラウンド・決めた前提の書き方）と、それを検証するテストです。インストーラとリリースツールは参照先 deep-spec-analysis を写す（ADR-001・ADR-002）ので、ここでは聞きません。以下は、要求整理で挙動設計へ先送りした 2 点（OQ4: 5 段階の判定文、OQ5: ラウンドの検証方法）を含む 5 問です。

Depth は Standard なので、決定の大きさが M までのものを人に聞き、S 以下は推奨回答で決めて末尾の「決めた前提」に書きました（要求 FR8.7 の規則をこの質問票にも当てはめています）。事実（参照先の provenance の項目、更新時の処理の中身）は調べて埋めてあります。

各質問の `[Answer]:` に選択肢の文字（例: `A`）を記入してください。当てはまらない場合は `X` を選び、内容を書き添えてください。

## Q1. 決定の大きさ（XL / L / M / S / SS）の判定文をどう書きますか？

要求 FR8.7 は 5 段階の定義を断片に書くことを求めていますが、エージェントが個々の決定をぶれずに当てはめるための判定文（例・反例）は挙動設計で決めることになっていました（OQ4）。断片は 28 ステージすべてに同じ文が入るので、長さも効きます。

A. 2 つの問いかけで段階を決める — 「変えるとどこまで影響するか（他の構成要素の契約まで / 同じ構成要素の中 / その場だけ）」と「あとで戻せるか（高くつく / 数分で戻せる / 利用者には見えない）」。各段階に判定の問いかけ 1 行と、例・反例を 1 つずつ付ける
B. 段階ごとに例を 3 つずつ並べ、問いかけは書かない（例から類推させる）
C. 「戻すのにかかる時間」だけで線を引く（XL: 日単位、L: 半日、M: 1 時間、S: 数分、SS: 秒）
D. Not yet defined（まだ決めていない）
X. Other (please specify)

[Answer]: A

## Q2. 「決めた前提」（Depth の閾値より小さいので、エージェントが推奨回答で決めた決定）を質問ファイルにどう書きますか？

要求 FR8.7 は「決めた前提」を質問ファイルに明示し、最後の確認（consolidated summary）で一括確認するとしています。人が「その前提は違う」と言ったときの戻し方もここで決めます。この質問票の末尾にある「決めた前提」は、選択肢 A の形で書いてあります。

A. ラウンドごとに、そのラウンドの質問の直後に `### 決めた前提（ラウンド n）` の見出しを置き、1 件 1 行で「[大きさ] 決定の内容 — 理由」と書く。最後の確認の要約に「決めた前提」の節を設けて全件を並べ、人が Request changes で 1 件を挙げたら、その決定を次のラウンドの質問に格上げして聞き直す
B. 質問ファイルの末尾に 1 つの節「決めた前提」としてまとめる（ラウンドとの対応は書かない）。異議は A と同じく質問に格上げする
C. 決めた前提も普通の質問として書き、`[Answer]:` にエージェントが推奨回答を書いて、直下に `**Mode:** grill (auto)` を付ける
D. Not yet defined（まだ決めていない）

## Q3. ライブ確認のテストで「1 回の画面に前提の揃った質問がまとまって出る」ことをどう検証しますか？

現在のテスト（`grilling/tests/live-claude.test.ts`）は「Grill me を選んだ後の画面 2・3 はそれぞれ 1 問」を検証しており、要求 FR1.4 でこれを置き換えます。要求整理では、1 ラウンド目の質問数の下限と、依存する質問が同じ画面に出ないことの検査方法を先送りしていました（OQ5）。ライブ確認は sonnet で 1 回 5 分程度・数ドルかかります。

A. Grill me を選んだ後の最初の画面に 2 問以上 4 問以下が並び、各質問の先頭選択肢に「(Recommended)」が付くことを検証する。続く画面も「4 問以下・先頭が (Recommended)」を検証する。質問どうしが独立かどうかはテストで機械判定せず、ライブ確認の記録に人が読んだ結果を書く
B. 1 問だけの画面も許容し、「(Recommended)」の位置だけを検証する（まとめて出す方式そのものは検証しない）
C. A に加えて、画面に出た質問文を別の LLM 呼び出しに渡して、独立かどうかを判定させる

## Q4. 調べれば分かること（事実）の結果を待っている質問は、質問ファイルでどう扱いますか？

要求 FR8.3 は「事実は聞かずに調べる」「調べ終わるのを待たず、残りの質問を先に出す」と定めています。Claude Code ではサブエージェントに調べさせるので、結果が返る前に画面を出す場面があります。

A. 調査待ちの質問は、空の `[Answer]:` と `**Pending:** <調べていること>` の行を付けて質問ファイルに先に追記し、結果が出た次のラウンドで出す。結果によって聞く必要がなくなった質問は「決めた前提」に移して理由を書く
B. 調査が終わるまで次のラウンドを出さない（同期。簡単だが、取り込み元の「待たない」と異なる）
C. 調査待ちの質問はファイルに書かず、結果が出てから初めて追記する

## Q5. 「1 問ずつ聞く」への切り替えは、何を見て判断しますか？

A. `## Corrections` に「Grill me（または grilling）は 1 問ずつ」の趣旨の行があれば切り替える。文言は意味で判断し、文字列の完全一致は求めない。会話中に人が「1 問ずつにして」と言えば、そのステージの残りも 1 問ずつにする（project.md への記録は §13 の学びの儀式に任せる）

### 決めた前提（ラウンド 1）

Depth が Standard なので、大きさ S 以下の決定は推奨回答で決めました。最後の確認でまとめて確認します。異議があれば質問に格上げします。

- [S] インストーラの provenance の項目は参照先と同じ 5 項目 — `version` / `ref`（解決した選択子の値）/ `source`（`local` | `ref` | `tag` | `latest`）/ `installed_at` / `payload_sha256`。ハーネスは保存先パス（`<harness>/tools/data/grilling-install.json`）で分かるので項目にしない — 理由: 参照先を写す（ADR-001）。要求 FR4.3 の 4 項目（バージョン・選択子・時刻・ダイジェスト）を満たす
- [S] 更新時の「以前 compose した自分のファイルを消して置き直す」処理（要求 OQ2・前提 A2）は残すが何もしない — 参照先は sensors / tools / knowledge / agents / scopes / stages の自前ファイルだけを消す。grilling は contributions のみでこれらを持たないため対象がなく、廃止済みファイルの一覧（tombstone）も空にする — 理由: 写す範囲を変えない。contribution のマージは内容ベースで自動的に置き換わる
- [S] ルート README の「Adopting mid-project」（要求 OQ3）は「次の質問ステージ（単一ステージ実行を含む）から Grill me が現れる」とだけ書く — 単一ステージ実行（`/aidlc --stage <slug> --single` と `/aidlc-<stage>` runner）も同じステージファイルを読むので、特別な案内は不要 — 理由: 参照先の `--single` 案内に相当する仕組みが grilling 側にない
- [S] 画面分割時の書き戻しの単位は画面ごと — 5 問以上のラウンドを 4 問ずつに分けたときは、画面ごとに答えを受け取り次第 `[Answer]:` に書き戻し、`aidlc-log.ts decision` / `answer` も画面ごとに記録する（ラウンドの追記は提示前に 1 回） — 理由: 既存断片の「受け取り次第書き戻す」規則に合わせる
- [S] 番号付きプローズ（Claude Code 以外）での推奨回答は取り込み元の `➡️` 行で示し、選択肢の並びは変えない（Claude Code だけ推奨を先頭に置く） — 理由: 要求 FR8.2 の書式に従う
- [S] 質問番号（Qn）はファイル全体で通し、ラウンドは `## ラウンド n` の見出しで区切る — 理由: 「1 は A、2 は B」と番号で答えられる取り込み元の利点を保つ
